IM 开放平台 · 第三方接入

任何第三方业务系统（SaaS / 打车 / 电商 / 本地生活等）按标准 5 步流程接入 IM：申请 → 审核 → 用户授权 → 后台换证 → 用户同步与业务打通。第三方系统保有独立业务闭环，脱离 IM 也能完整运行。

接入总览与流程

开放平台提供两条互补路径：只要 C 端入口与跳转的走轻量层，需要 IM 账号登录与用户同步的走重量层 OAuth 接入。两条路径独立启用，可以叠加。

两条接入路径

路径适用场景需要账号互通说明
A. 服务板块服务项（轻量）只需在 IM 的 C 端「服务板块」有入口、能跳转否见本页「服务板块接入（轻量层）」
B. 开放平台 OAuth（重量）要用 IM 账号登录你的系统、同步昵称 / 头像 / 手机号，后续做消息触达是本页其余章节

标准接入流程（5 步）

1

应用申请

准备主体、应用名、HTTPS 回调地址与最小 scope，调用 POST /open/applications 提交，拿到 appId（状态 PENDING）。

2

平台审核

平台运营在 IM 管理后台「第三方接入」页通过或驳回；通过后交付 appId / appSecret（仅一次）。

3

用户授权

前台：跳转 /oauth/authorize（PKCE S256 + state），用户同意后回调拿到一次性 code。

4

后台换证

你的服务端用 code + code_verifier 换 token、取 userinfo、建 / 绑账号——appSecret 只在这里使用。

5

用户同步与业务打通

授权范围内按契约订阅同步；第三方业务独立闭环，最后按自测 / 验收清单验证。

  • 全程只有第 3 步（平台审批）需要平台侧介入，其余都可自助完成。
  • appSecret 只在审批通过或重置密钥时返回一次，且只能保存在你的服务端，H5 / App / 小程序不得持有。

申请与审批：提交什么 · 谁审 · 多久 · 通过后拿到什么

应用注册不等于授权。提交申请只产生一条待审记录，必须经平台审批通过才会发放密钥。

一、提交什么（材料清单）

材料要求
appName应用名称（必填）：会展示在用户授权页，请用真实业务名，不要使用「测试」「demo」等占位名。
subjectName接入主体（企业 / 组织名，审核用），需与商务主体一致。
appType第三方填 THIRD_PARTY；FIRST_PARTY 仅平台自用。
callbackUrlHTTPS 回调地址：无 fragment（#）、生产域名；与线上实际页面逐字符一致（含尾斜杠）。
scopes最小授权，从下方 scope 清单中选择；申请 profile.phone 需说明用途，notify 当前不开放。
联系方式技术对接人 + 邮箱 / 手机，便于审核有疑问时联系。

二、怎么提交、怎么跟踪

POST {IM_BASE}/open/applications
Content-Type: application/json

{
  "appName": "A380 智慧门店",
  "subjectName": "深圳某某科技有限公司",
  "appType": "THIRD_PARTY",
  "callbackUrl": "https://miniservice.example.com/a380/",
  "scopes": ["profile.basic"]
}

# 响应（不含密钥，此时为 PENDING）
{ "appId": "app_3f7c9a21", "appName": "A380 智慧门店", "status": "PENDING", "appSecret": null }

# 轮询审核状态
GET {IM_BASE}/open/applications/{appId}
{ "appId": "app_3f7c9a21", "status": "PENDING", "rejectReason": null, "scopes": ["profile.basic"], "callbackUrl": "https://miniservice.example.com/a380/" }

{IM_BASE} 为平台交付的网关域名（文档示例：https://api.example.com），本地联调可换成联调网关地址。网关已直通路由：/open/**、/oauth/**、/.well-known/openid-configuration，路径不带 /api。

四、谁审、怎么审、多久

环节责任方建议时效
材料齐全性初判平台商务 / 对接人1 个工作日
技术项审核（回调地址、scope 最小化）平台运营 / 研发1 个工作日
通过后交付密钥平台运营审核通过后当天
联调支持双方研发按项目排期

审核在 IM 管理后台「第三方接入」页完成：筛选「第三方 + 待审核」，逐项核对主体、回调地址与 scope，然后「通过」或「驳回」。第三方无权调用审核接口。

逐项判定标准：主体真实且有商务关系；回调地址为 HTTPS 生产域名、无 #、与业务页面一致；scope 只申请必要项；应用名为用户可理解的业务名；appType 正确；同一主体不重复申请。

被驳回时会给出可直接执行的 rejectReason（例如「回调地址需为 HTTPS 生产域名且与线上页面一致」），按原因修正后重新提交即可，同一主体可再次申请。

五、审批通过后拿到什么（密钥交付规则）

  • 拿到 appId 与批准信息（应用名、主体、回调地址、批准的 scope）。
  • appSecret 只在「通过」或「重置密钥」的响应里出现一次，平台不提供二次查看。
  • 平台通过安全渠道交付（密码管理器 / 加密消息），不要用普通聊天工具明文发送或截图。
  • appSecret 只能放在你的服务端密钥管理里；客户端（H5 / App / 小程序）不得持有。
  • 怀疑泄露时请平台「重置密钥」，旧密钥立即失效；平台只保存不可逆哈希。

六、变更、重置与吊销

场景动作影响
更换回调地址 / 增加 scope当前没有公开的自助修改端点，由平台按变更流程处理（必要时驳回后重新申请）变更前旧配置继续生效
密钥疑似泄露平台「重置密钥」旧密钥立即失效，你需更新服务端配置
合作终止 / 违规平台「吊销」状态 SUSPENDED，该应用全部 token 与授权失效；你的业务数据保留

前后台两段接入的差异（最容易搞错的地方）

接入被拆成两段：前台「用户在场，只拿 code」，后台「服务端对服务端，持有密钥、换 token、取资料」。混用这两段是接入失败的主要原因。

维度前台 / Front channel后台 / Back channel
运行位置浏览器 / WebView / App你的服务端
用户是否在场在（要点「同意」）不在（静默调用）
是否持有 appSecret绝不只在这里
用到哪些接口GET /oauth/authorize、GET /oauth/consent（同意页）POST /oauth/token、GET /oauth/userinfo、POST /oauth/revoke、GET /.well-known/openid-configuration
关键参数appId、redirect_uri、scope、state、code_challenge + code_challenge_method=S256、noncegrant_type=authorization_code、code、redirect_uri、app_id、code_verifier；userinfo 用 Authorization: Bearer <access_token>
输入 / 输出输入 appId + scope + redirect_uri + PKCE challenge；输出一次性 code（+ state）输入 code + code_verifier + app_id；输出 access_token / refresh_token / open_id / id_token
能否取用户资料否是（GET /oauth/userinfo）
失败重试重新跳授权（幂等）code 不可重放；token 过期用 refresh_token 续期
常见错误redirect_uri 不精确匹配、缺 state、把密钥写进前端用错 code_verifier、重复使用 code、漏校验 state

参数速查

参数所属说明
appId前台审核通过的应用标识；使用标准 OIDC 客户端库时，其 client_id 与本平台 appId 对应。
redirect_uri前台 + 后台与登记的 callbackUrl 逐字符一致（含尾斜杠、端口、大小写）。
scope前台 + 后台只能是你被批准的 scope；后台响应会回显实际授权范围。
state前台发起、后台校验随机串防 CSRF，回调原样带回；不匹配必须丢弃。
code_challenge / code_challenge_method前台PKCE，仅支持 S256；challenge = BASE64URL(SHA256(code_verifier))，无填充。
nonce前台（推荐）OIDC id_token 防重放。
code前台产出、后台消费一次性授权码，短期有效；只在回调 URL 上出现，重复使用必须被拒绝。
code_verifier后台PKCE 原始随机串（43–128 字符），自己留好，只在换 token 时提交。
open_id后台返回IM 用户在你的应用下的稳定唯一标识，请用它作为账号绑定键。
access_token / refresh_token / expires_in后台返回令牌为不透明字符串，有效期 7200 秒；过期用 refresh_token 续期。
appSecret仅后台服务端请求凭据（如 HTTP Basic 或服务端参数），任何情况下都不进入 H5 / App。

A380 完整接入示例（端到端）

A380 智慧门店（SaaS 平台）是开放平台的第一个第三方接入方：前台是运行在 IM 客户端内的 H5，后台是 A380 的身份服务。下面这条链路已在真实环境跑通，可作为你的接入参考。

1. 申请与审批

项值
应用A380 智慧门店（appType = THIRD_PARTY）
appIdapp_3f7c9a21
回调地址https://miniservice.example.com/a380/（HTTPS，与线上 H5 页面逐字符一致，含尾斜杠）
scopeprofile.basic（仅昵称 / 头像，够用就不多要）
审批IM 管理后台「第三方接入」页通过 → 平台通过安全渠道把 appId / appSecret 交付给 A380 服务端
 
# 1) 提交申请（拿到 appId，状态 PENDING）
POST {IM_BASE}/open/applications
{
  "appName": "A380 智慧门店",
  "subjectName": "深圳某某科技有限公司",
  "appType": "THIRD_PARTY",
  "callbackUrl": "https://miniservice.example.com/a380/",
  "scopes": ["profile.basic"]
}
# → { "appId": "app_3f7c9a21", "status": "PENDING", "appSecret": null }

# 2) 轮询状态，直到 APPROVED
GET {IM_BASE}/open/applications/app_3f7c9a21
# → { "appId": "app_3f7c9a21", "status": "APPROVED", "rejectReason": null, "scopes": ["profile.basic"], "callbackUrl": "https://miniservice.example.com/a380/" }

2. 前台：H5 拿 code

H5 通过容器原生桥（见下方「H5 内嵌 WebView 授权」）或直接跳转授权地址，用 PKCE S256 + state 拿到一次性 code。

GET {IM_BASE}/oauth/authorize
  ?appId=app_3f7c9a21
  &redirect_uri=https%3A%2F%2Fminiservice.example.com%2Fa380%2F
  &scope=profile.basic
  &state=STATE_RANDOM
  &code_challenge=CODE_CHALLENGE_S256
  &code_challenge_method=S256
  &nonce=NONCE_OPTIONAL

# 用户同意后 302 回：
#   https://miniservice.example.com/a380/?code=AUTH_CODE&state=STATE_RANDOM
# 用户拒绝：
#   https://miniservice.example.com/a380/?error=access_denied&state=STATE_RANDOM

3. 后台：换 token（IM 侧）

A380 服务端校验 state 后，用 code + code_verifier 调 IM 换 token，并用 open_id 作为自己系统里的绑定键。

POST {IM_BASE}/oauth/token
Content-Type: application/x-www-form-urlencoded      # 也支持 application/json

grant_type=authorization_code
&code=AUTH_CODE
&redirect_uri=https%3A%2F%2Fminiservice.example.com%2Fa380%2F
&app_id=app_3f7c9a21
&code_verifier=CODE_VERIFIER

# 响应
{
  "access_token": "...", "refresh_token": "...", "expires_in": 7200,
  "open_id": "op_9c1f...", "scope": "profile.basic",
  "id_token": "eyJ...", "token_type": "Bearer"
}

4. 后台：A380 身份服务的授权码回调（A380 侧实现）

POST /api/v1/identity/oauth/im/callback
Content-Type: application/json

{
  "code": "AUTH_CODE",
  "code_verifier": "CODE_VERIFIER",
  "redirect_uri": "https://miniservice.example.com/a380/",
  "app_id": "app_3f7c9a21",
  "state": "STATE_RANDOM",
  "nonce": "NONCE_OPTIONAL"
}

服务端行为（真实实现）：

  1. 校验 state；
  2. 用 code + code_verifier 调 IM 的 POST /oauth/token；
  3. 按 open_id 建立 / 绑定 A380 账号；
  4. 种 HttpOnly 会话 Cookie 并把 authenticated=true 返回给 H5，之后业务请求只带这个会话，不再每次问 IM。

A380 的 C 端与 B 端使用不同 appId 区分，会话 Cookie 也分两套。旧版「直传 im_access_token」的绑定入口已停用（返回 410 LEGACY_BIND_DISABLED），新接入请统一使用授权码回调。

5. 后台：取用户资料

GET {IM_BASE}/oauth/userinfo
Authorization: Bearer ACCESS_TOKEN

# 响应（只返回授权范围内的字段；phone 已脱敏）
{
  "open_id": "op_9c1f...",
  "nickname": "张三",
  "avatar": "https://cdn.example.com/avatar/10086.png",
  "phone": "138****5678"
}

6. 验收时的表现

  • 用户从 IM 进入门店 H5 → 授权一次 → 门店内已完成登录，无需在门店侧再注册 / 登录。
  • 用户在 IM 侧解除授权后：门店业务数据仍在，门店登录态失效，需重新授权。
  • IM 不可用时，门店已有登录态的用户仍能继续使用门店业务。

授权流程

OAuth 2.0 Authorization Code + PKCE（OIDC）：

  • 客户端注册：公开客户端（H5 / App / WebView）使用 PKCE，不携带 secret；confidential 服务端的 appSecret 只留在服务端。
  • 用户级授权：第三方引导用户授权指定 scope，用户可随时在 IM 侧撤销。

时序

  1. 1第三方 App→IM
    GET /oauth/authorize?appId&scope&redirect_uri&state&nonce&code_challenge&code_challenge_method=S256
  2. 2IM→用户
    跳转用户同意页 /oauth/consent（展示应用名 + scope 中文说明）
  3. 3用户→IM
    用户同意，302 回 redirect_uri?code=...&state=...（拒绝则 error=access_denied）
  4. 4第三方 App→IM
    POST /oauth/token（code + PKCE verifier + app_id）
  5. 5IM→第三方 App
    返回 access_token / refresh_token / expires_in / open_id / id_token
  6. 6第三方 App→IM
    GET /oauth/userinfo（Authorization: Bearer access_token）

前台红线

  • 绝不把 appSecret 放在前台代码里（WebView / H5 / App 都是 public client）。
  • state 必须校验；code 只能用一次；回调只认与登记值逐字符一致的 redirect_uri。
  • 授权失败或用户拒绝要有明确页面提示，不要停在空白回调页。

H5 内嵌 WebView 授权（原生桥 · 小程序模型）

第三方业务以 H5 页面内嵌在 IM App WebView 中运行时（本地生活 / KTV / 酒店 / 打车等小程序），通过容器注入的原生桥完成「IM 用户 → 第三方用户」授权登录，对齐小程序模型：H5 调桥拿 code，你的服务端换 token 并建立自己的会话。

时序

  1. 1IM App（容器）→WebView
    注入 window.GVBridge.login({ appId, scope, redirectUri })
  2. 2第三方 H5→IM App
    GVBridge.login()：App 原生用自己的登录态走 /oauth/authorize 拿 code
  3. 3IM App→第三方 H5
    返回 { code, code_verifier, redirect_uri }
  4. 4第三方 H5→第三方后端
    POST 你的服务端授权码回调接口（body: code + code_verifier + redirect_uri）
  5. 5第三方后端→第三方 H5
    换 token + 建 / 绑账号 → 下发 HttpOnly 会话 Cookie（H5 不保存 JWT）

关键点

  • IM 的用户登录态不出 App：App 原生只在桥内用它拿 code，不进入 H5 的 JS、不进 URL。
  • code 一次性、短期有效；回调成功后由你的服务端通过 HttpOnly Cookie 保存会话，H5 不保存 JWT。
  • 登录态有效性：业务请求使用你自己的会话；会话过期、撤销或应用切换时重新 GVBridge.login()，不必每次请求 IM。
  • redirectUri 为 H5 自身 URL，须与开放平台登记的 callbackUrl 精确一致（含尾斜杠）。

profile.basic昵称 / 头像已开放
profile.phone手机号（脱敏展示），需说明用途已开放
notify站内信 / 推送预留，暂不开放（申请会被驳回）

用户同步

  • 拉取（Pull）：GET /oauth/userinfo（授权范围内）。
  • 订阅（Subscribe）：UserProfileChanged 事件（topic 见 OpenAPI / AsyncAPI 契约）。
  • 同步内容仅限授权范围（昵称 / 头像 / 手机号脱敏）；不共享 IM 聊天 / 好友 / 群组数据。
  • 解绑 / 撤销：第三方业务数据保留，仅移除 IM 登录 / 触达方式。

安全与数据边界

  • appSecret 以不可逆哈希保存，不落明文、不进日志、不进客户端，只在审核通过或重置时返回一次。
  • scope 最小授权，超范围请求会被拒绝；授权 / 撤销 / 解绑立即失效。
  • 审计：授权 / 撤销 / 同步 / 触达均记审计；日志脱敏（不落 token / 手机号明文）。
  • 共享范围仅限授权 scope（昵称 / 头像 / 脱敏手机号）；不共享聊天、好友、群组数据。
  • 解绑 / 撤销后第三方业务数据保留。

服务板块接入（轻量层 · 小程序服务项）

打车、外卖、电商、本地生活等外部服务，若只需在 C 端「服务板块」展示入口并跳转（无需 OAuth 账号授权），走更轻量的「服务项（小程序）」接入。

C 端入口链路

App 头部 A380 板块 → 服务页（服务板块）→ 服务类型分组 → 服务项（小程序），点击跳转小程序 / H5 / 自定义 scheme。

  • C 端头部 A380 板块 → 服务页验证入口与跳转。
  • 如需 IM 账号互通 / 用户同步，再叠加上方开放平台 OAuth 接入。

上线前自测清单（可复制）

用下面的最小闭环脚本，在自己的联调环境把「申请 → 轮询 → 授权 → 换 token → 取资料 → 撤销」跑通一遍。

IM_BASE=https://api.example.com
APP_ID=app_3f7c9a21
REDIRECT=https%3A%2F%2Fminiservice.example.com%2Fa380%2F

# 0) 生成 PKCE
VERIFIER=$(openssl rand -base64 48 | tr -d '=+/' | cut -c1-64)
CHALLENGE=$(printf '%s' "$VERIFIER" | openssl dgst -binary -sha256 | openssl base64 | tr '+/' '-_' | tr -d '=')
STATE=$(openssl rand -hex 16)

# 1) 提交申请（首次）→ 记下 appId，等待平台在 IM 管理后台「通过」
curl -s -X POST "$IM_BASE/open/applications" -H 'Content-Type: application/json' \
  -d '{"appName":"联调应用","appType":"THIRD_PARTY","callbackUrl":"https://miniservice.example.com/a380/","scopes":["profile.basic"]}'

# 2) 查状态（APPROVED 之后才继续）
curl -s "$IM_BASE/open/applications/$APP_ID"

# 3) 打印授权地址，浏览器打开并同意（拿到回调里的 code）
echo "$IM_BASE/oauth/authorize?appId=$APP_ID&redirect_uri=$REDIRECT&scope=profile.basic&state=$STATE&code_challenge=$CHALLENGE&code_challenge_method=S256"

# 4) 用 code 换 token（后台）
curl -s -X POST "$IM_BASE/oauth/token" -H 'Content-Type: application/x-www-form-urlencoded' \
  -d "grant_type=authorization_code" -d "code=$CODE" -d "redirect_uri=$REDIRECT" \
  -d "app_id=$APP_ID" -d "code_verifier=$VERIFIER"

# 5) 取用户资料
curl -s "$IM_BASE/oauth/userinfo" -H "Authorization: Bearer $ACCESS_TOKEN"

# 6) 撤销
curl -s -X POST "$IM_BASE/oauth/revoke?token=$ACCESS_TOKEN"
  • code_verifier 为 43–128 字符随机串；code_challenge = BASE64URL(SHA256(code_verifier))，要去掉填充。
  • code 只能用一次且短期有效，重放必须被拒绝；state 不匹配必须直接丢弃。
  • 申请未通过（PENDING / REJECTED）时不要引导用户去授权，授权页会提示应用不可用。

验收清单（平台侧验收标准）

  • 申请 → 审批 → 拿到 appId / appSecret，且密钥只在服务端（前端 grep 不到）。
  • redirect_uri 与登记 callbackUrl 精确一致；不一致时被拒绝且提示可读。
  • 首次授权：用户同意 → 回调 code → 换 token → 取 userinfo → 建 / 绑账号 → 你的登录态生效。
  • 用户拒绝授权：回调带 error=access_denied，页面有明确提示。
  • state 不匹配或 code 重放：请求被拒绝。
  • 撤销 token 后 userinfo 失效；用户解除授权后你的登录态失效，业务数据保留。
  • IM 不可用时，已有登录态的用户仍能完成你的核心业务闭环。
  • 密钥泄露演练：平台重置密钥后旧密钥立即失效。

错误码与排障

现象原因处理
申请被驳回（REJECTED）材料不全 / scope 过大 / 回调非 HTTPS看 rejectReason，修正后重新申请
授权页报应用不可用appId 不存在或不是 APPROVED 状态用 GET /open/applications/{appId} 查状态
redirect_uri 校验失败与 callbackUrl 不完全一致（尾斜杠 / 端口 / 大小写）改成逐字符一致
换 token 失败code 已用过或过期；code_verifier 与 challenge 不匹配code 只能用一次；verifier 用原始串
userinfo 返回 401access_token 过期或已撤销用 refresh_token 续期或重新授权
